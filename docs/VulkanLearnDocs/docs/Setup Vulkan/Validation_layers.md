# 验证层

## Vulkan Layer

Vulkan 中的层是一个可选的中间件，它们“插入”到应用程序和 Vulkan 驱动程序之间，用来拦截、检查或修改 Vulkan API 调用。

### 1. 层的设计

将 Vulkan 的 API 调用想象成一个管道：
[应用程序] -> [Vulkan 驱动程序] -> [GPU 硬件]
发布” (Release) 模式下，这就是完整的流程。驱动程序会假设您的代码是完美的，它会以最快的速度执行命令，几乎不做任何错误检查，以实现最低的 CPU 开销。

但是，在开发过程中，您需要知道自己是否用错了 API。这时，“层”就登场了。当您启用一个层（比如最著名的“验证层”）时，这个管道会变成：
[应用程序] -> [层] -> [Vulkan 驱动程序] -> [GPU 硬件]


#### 层可扩展性和灵活性

- “层”系统是完全可插拔的。任何人都可以编写自己的层来实现特定功能，而无需修改 Vulkan 驱动或应用程序本身。
- 这催生了一个强大的工具生态系统，而不仅仅是 Khronos 官方的验证层。


### 2. 验证层

- 在开发时，您可以启用所有验证层，获得最严格的调试支持。而在发布应用程序时，您只需完全禁用这些层，就能获得一个“零开销”的、性能极致的驱动程序。

- 通过“验证层”，Khronos 提供了一套标准化的、跨厂商的调试工具 (VK_LAYER_KHRONOS_validation)。无论您在哪家厂商的 GPU 上开发，都能得到一致的、高质量的 API 用法反馈。

- 这是一个集合层，包含了对 API 用法、对象生命周期、线程安全等几乎所有规范内容的检查。在开发 Vulkan 程序时，这个层应该始终开启。

如果验证层发现问题，它会通过调试回调机制向您的程序报告一个详细的错误或警告。如果一切正常，它再把这个 API 调用原封不动地传递给驱动程序。

多个层可以像洋葱一样叠加在一起，形成一个“调用链” (Call Chain)。


### 3. 三方工具

- RenderDoc、NVIDIA Nsight、AMD RGP 等图形调试器和性能分析器也会利用“层”机制来注入它们自己的代码，以便捕获和分析一帧画面的所有渲染数据。

### 4. 常见层

#### VK_LAYER_LUNARG_api_dump

- 一个简单的工具层，它会将程序调用的每一个 Vulkan API 及其参数打印到控制台或文件中。这对于追踪程序执行流程非常有用。

#### VK_LAYER_LUNARG_monitor

- 一个用于在桌面上显示帧率 (FPS) 的简单层

### 显式层与隐式层

Vulkan 的层根据其加载方式被分为两类，这种区分对于排查“为何我的程序崩溃但代码没问题”这类问题至关重要。

- 显式层（Explicit Layers）： 这些层必须由应用程序在 VkInstanceCreateInfo 中显式请求。验证层就属于这一类。如果应用程序不请求，它们就不会加载。

- 隐式层（Implicit Layers）： 这些层如果存在于系统中，通常会被加载器自动加载，无需应用程序干预 。
典型例子： Steam 覆盖层（VK_LAYER_VALVE_steam_overlay）、FPS 计数器（如 FRAPS 或 NVIDIA Nsight）、以及某些捕捉工具（如 RenderDoc 的注入层）。

    - 发现机制： 隐式层通过特定的操作系统位置注册。在 Windows 上，它们位于注册表中；在 Linux 上，它们位于特定的 /etc/vulkan/implicit_layer.d 或用户目录中 。

    - 风险与管理： 隐式层是造成 Vulkan 应用程序不稳定的常见原因。一个有 bug 的隐式层可能会导致完美的应用程序崩溃。开发者在调试难以复现的崩溃时，通常需要通过设置环境变量（如 VK_LOADER_LAYERS_DISABLE=~implicit~）来禁用所有隐式层以隔离问题 。
